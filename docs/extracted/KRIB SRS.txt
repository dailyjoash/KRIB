This document is intended for the project supervisor, software developers, and system designers to ensure a clear understanding of the system's deliverables and capabilities.  1.2 Scope The system to be produced is named KRIB, a digital rental management platform. What the system will do: The system will automate rent collection, facilitate real-time communication between landlords and tenants, provide secure storage for documents (leases/receipts), and track maintenance requests. What the system will not do: The system is limited to urban and peri-urban areas and requires internet connectivity; it does not function as an offline-first application. Benefits: It aims to solve the inefficiencies of manual record-keeping, missed rent payments, and poor communication channels in the Kenyan rental market.  1.3 Definitions, Acronyms and Abbreviations Definitions KRIB – A digital rental management system designed to automate rent payments, manage tenant– landlord interactions, and track maintenance requests. Landlord – A registered system user who owns or manages rental properties and oversees tenants and payments. Tenant – A registered system user who occupies a rental property and uses the system to pay rent and submit maintenance requests. Lease – A formal agreement between a landlord and a tenant that defines the rental terms and conditions. Rent – The periodic payment made by a tenant to a landlord for occupying a rental property. Arrears – The outstanding rent amount that remains unpaid after the due date. Maintenance Request – A request submitted by a tenant to report an issue requiring repair or servicing in a rental property. Dashboard – A graphical user interface that displays summarized system information based on user roles. Notification – A system-generated alert sent to users via SMS or in-app messaging to communicate important updates. 1.4 Overview The remainder of this document is organized as follows: Chapter 2 describes the general factors that affect the product and its requirements, including user characteristics and constraints. Chapter 3 details the specific functional and non-functional requirements, including interface specifications.  2.0 General Description 2.1 System Perspective The KRIB system is a distributed, web-based application utilizing a Client-Server architecture. It interacts with external payment interfaces (M-Pesa, PayPal) and cloud hosting services (AWS/DigitalOcean). Principal Interfaces: The system interfaces with the M-Pesa API for transactions and an SMS gateway for notifications. Hardware: The system is hosted on cloud servers and accessed via client devices (smartphones/desktops).   2.2 System Functionality The system will perform the following functions: Rent Payment Processing: Automates calculation and collection of rent via integrated APIs. Maintenance Tracking: Allows tenants to submit requests and landlords to update status. Document Management: Securely uploads and stores lease agreements and receipts. Communication: Enables real-time chat and SMS notifications between parties. Dashboard Analytics: Displays payment history and arrears on role-based dashboards.   2.3 User Characteristics Landlords: Typically property owners seeking to reduce administrative burden. They require accurate financial tracking and tenant oversight capabilities. Tenants: Residents seeking convenience in payments and quick responses to maintenance issues. They may vary in technical expertise but generally possess basic smartphone skills.   2.4 General Constraints Connectivity: The system functionality is strictly dependent on stable internet connectivity. Hardware: Users must possess internet-enabled devices (smartphones or computers). Regulatory: The system must comply with data protection laws regarding personal tenant information.  2.5 Assumptions and Dependencies It is assumed that the target users (landlords/tenants) have basic digital literacy to navigate a web interface. The system depends on the uptime of third-party APIs (M-Pesa daraja, PayPal) for payment processing.    3.0 Specific Requirements 3.1 Functional Requirements 3.1.1 Rent Payment Module Inputs: Payment amount, Payment Method (M-Pesa/Card), Tenant ID. Processing: The system validates the account balance via API, processes the deduction, and updates the database record. Outputs: Digital Receipt, SMS Confirmation, Updated Dashboard Balance  3.1.2 Maintenance Module Inputs: Description of issue, Photo evidence (optional), Urgency level. Processing: System logs the request and triggers a notification to the specific landlord. Outputs: Status update (e.g., "Pending", "Resolved") on the tenant dashboard.  3.2 User Interface Requirements Web Interface: The frontend will be developed using React.js to provide a responsive, mobile-friendly user experience. Dashboards: Distinct views for Landlords (Revenue focus) and Tenants (Payment/Request focus).  3.3 Hardware & Software Interfaces Software: Backend runs on Python (Django REST Framework); Database is PostgreSQL. Communication: The system requires HTTP/HTTPS protocols for web traffic and API calls.
