No software installation is required for end users.  Activities of Conversion Conversion refers to the transition from the existing manual rental management processes used by landlords and tenants in Kenya to the KRIB digital platform. The following conversion activities will be carried out:  Data Digitisation Landlords will be assisted in entering their existing property and tenant records into the KRIB system during the onboarding phase. This includes property names, locations, rent amounts, and tenant contact details. Historical payment records, where available, will be entered into the system to provide landlords with an initial payment history baseline. Lease agreements will be scanned or digitally uploaded into the Document Management Module.  System Conversion Strategy KRIB will adopt a Direct Conversion strategy for system deployment. Under this approach: The KRIB platform will be deployed as the primary rental management tool from a set go-live date. Manual processes (handwritten records, cash rent collection) will be phased out as landlords and tenants are onboarded to the platform. A backup of all digitised data will be created before the go-live date and stored securely to prevent data loss during conversion. The system will be deployed first in a beta testing environment, where a small group of landlords and tenants will use the platform and report any issues before full rollout.  Environment Variable Configuration Before deployment, the following environment variables must be configured on the production server: DATABASE_URL — Connection string for the PostgreSQL database. SECRET_KEY — Django security key. MPESA_CONSUMER_KEY and MPESA_CONSUMER_SECRET — Credentials for the M-Pesa Daraja API. PAYPAL_CLIENT_ID and PAYPAL_CLIENT_SECRET — Credentials for PayPal integration. JWT_SECRET — Secret key for JSON Web Token generation.  Training Plan  Training Objectives The training plan for KRIB is designed to ensure that all users — landlords and tenants — are able to use the platform confidently and independently. By the end of training, users should be able to: Register and log in to KRIB. Navigate their role-specific dashboard. Perform key tasks: paying rent, submitting maintenance requests, and accessing documents (Tenants); adding properties, managing tenants, and viewing reports (Landlords). Understand common error messages and how to resolve them.  Training Methods Training will be delivered using the following methods:  User Training Manual: A comprehensive User Training Manual (this project's User Manual deliverable) will be provided to all users. It contains step-by-step instructions with clear language, covering all KRIB features for both Landlords and Tenants.  Hands-On Demonstration: An initial walkthrough session will be conducted with a representative group of landlords and tenants during the beta testing phase. The developer will guide users through the platform's key features in a live demonstration environment, allowing participants to ask questions and practice tasks.  In-App Guidance: The KRIB interface is designed to be intuitive, with clear labels, tooltips, and navigation menus that guide users through their tasks without requiring technical knowledge. Error messages are written in plain language and include actionable guidance.  FAQ Support: A Frequently Asked Questions section is included in the User Training Manual, addressing the most common user queries including payment failures, password resets, and lease activation.  Training Audience Audience Training Content Delivery Method Landlords Property management, tenant onboarding, payment monitoring, maintenance management, report generation. User Manual + Demonstration session. Tenants Registration, login, rent payment (MPesa/Card/PayPal), maintenance requests, document access. User Manual + Demonstration session.  Software Maintenance Plan After deployment, the KRIB system will require ongoing maintenance to ensure continued reliability, security, and performance. The software maintenance plan covers the following activities:  Corrective Maintenance Corrective maintenance involves identifying and fixing bugs and errors that arise during system use after deployment. Bug reports submitted by users or identified through system logs will be reviewed and prioritised by severity (Critical, Major, Minor). Critical bugs (e.g., payment failures, authentication errors) will be addressed within 24– 48 hours. Minor bugs (e.g., UI display issues) will be addressed in scheduled maintenance updates.  Adaptive Maintenance Adaptive maintenance configurations will be updated in line with AWS or DigitalOcean platform changes.  Perfective Maintenance Perfective maintenance involves improving the system based on user feedback and evolving requirements: New features (e.g., advanced analytics, automated lease renewal alerts) may be added in future iterations based on user feedback. Performance optimisations will be applied as the user base grows to maintain acceptable response times.  Maintenance Schedule Activity Frequency Responsible Party Bug review and patching As needed (critical: within 48 hrs) Developer controlled, communicated, and implemented after deployment. This ensures that any modifications to the system are made in an orderly and traceable manner.  Change Request Process Identification: A user, supervisor, or developer identifies a need for a change (bug fix, new feature, or system modification). Documentation: The change is documented in a Change Request form, describing the nature of the change, its justification, and its expected impact on the system. Review: The change request is reviewed for feasibility, impact on existing functionality, and alignment with project objectives. Approval: Changes are approved by the project supervisor before implementation. Implementation: Approved changes are implemented in a development environment and tested before being deployed to production. Version Control: All code changes are tracked using Git. Each change is committed with a descriptive message, and version tags are applied to major releases. User Notification: Where changes affect how users interact with the system, users are notified via in-app notification or email before the update is applied.  Version Control Strategy The KRIB codebase is maintained in a Git repository throughout the project lifecycle. All feature additions and bug fixes are developed in separate branches and merged into the main branch after testing and review. Release versions are tagged using semantic versioning (e.g., v1.0.0 for initial release, v1.1.0 for minor updates). A changelog is maintained to document all changes applied to the system in each version.  Budget Summary  Item Estimated Cost (KES) Notes Domain Registration & Hosting (AWS/DigitalOcean) 7,000 Annual subscription. Software Tools & API Licences (M-Pesa sandbox, etc.) 5,000 Developer accounts. Internet & Utilities (development and testing) 8,000 Data bundles, electricity. Testing & Deployment 6,000 Testing environment setup. Miscellaneous 4,000 Printing, stationery. Total Estimated Cost 30,000 KES  
