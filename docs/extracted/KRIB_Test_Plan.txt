It provides a structured approach to verifying that the system meets the functional and non-functional requirements defined in the KRIB Software Requirements Specification (SRS). The testing activities described here will ensure that all core modules — including authentication, rent payment, maintenance request management, and role-based dashboards — function correctly, securely, and reliably before deployment.  1.1 Goals and Objectives The overall goals and objectives of the KRIB testing process are: To verify that user authentication (registration and login) functions correctly and enforces role-based access for Landlords and Tenants. To confirm that the Rent Payment Module accurately processes transactions via MPesa, card, and PayPal, and generates correct digital receipts. To validate that the Maintenance Request Module allows tenants to submit, and landlords to update, maintenance requests with appropriate status tracking. To ensure the Document Management Module securely stores and retrieves lease agreements and payment receipts. To test notification delivery (SMS and in-app) for payment confirmations, arrears alerts, and maintenance updates. To identify, document, and resolve defects before the system is deployed to end users.  1.2 Statement of Scope Features to be tested: User registration and login with role assignment (Landlord / Tenant). Role-based dashboard display and navigation. Rent payment processing via M-Pesa API, card, and PayPal. Automated payment receipt generation and tenant/landlord notification. Arrears detection and automatic flagging of overdue accounts. Maintenance request submission, status updates, and landlord notification. Secure document upload and retrieval (lease agreements, receipts). System-generated SMS and in-app notifications.  Features NOT to be tested: Internal processing logic of third-party systems (M-Pesa Daraja API backend, PayPal infrastructure). Advanced reporting analytics beyond basic dashboard summaries (if not implemented in scope). Offline functionality (KRIB is an internet-dependent platform by design).  1.3 Major Constraints Testing time is limited to the project timeline, with a total testing window of approximately two weeks. The M-Pesa integration relies on the availability of the Safaricom Daraja sandbox environment, which may experience intermittent downtime. User Acceptance Testing will be conducted with a small group of simulated users rather than a full production user base, due to project constraints. The system is tested in a local development environment (localhost) prior to cloud deployment.  2.0 Test Plan This section describes the overall testing strategy and the project management approach for the KRIB system.  2.1 Software (SCIs) to be Tested The following software components of the KRIB system will be tested: KRIB Web Application — React.js frontend (responsive interface for Tenant and Landlord dashboards). KRIB Backend API — Django REST Framework backend (authentication, payment processing, maintenance, documents). PostgreSQL Database — Data storage for users, properties, leases, payments, and maintenance records. M-Pesa Daraja API Integration — Payment transaction processing. SMS Notification Service — Alert delivery to users.  2.2 Testing Strategy  2.2.1 Unit Testing Unit testing will be conducted on individual system components to ensure each module performs its intended function in isolation. Components to be unit tested include: Authentication Module: Registration form validation, login credential verification, JWT token generation. Rent Payment Module: Amount validation logic, API request construction, receipt generation. Maintenance Request Module: Request form validation, status update logic, notification trigger. Dashboard Module: Role-based data rendering for Tenant and Landlord views. Unit tests will be implemented using Django's built-in test framework for backend components and React Testing Library for frontend components.  2.2.2 Integration Testing Integration testing will confirm that the individual modules of KRIB work together correctly as a unified system. Key integration test scenarios include: Frontend login form → Backend authentication API → JWT token issued → Dashboard redirect. Tenant payment form → Django Payment API → M-Pesa Daraja API → Database payment record → Receipt generated. Maintenance request form → Backend logging → Landlord notification triggered. Document upload → Secure cloud storage → Retrieval by authorized user.  2.2.3 Validation Testing Validation testing will verify that the KRIB system satisfies the functional requirements documented in the SRS. Each functional requirement will be tested to confirm the system delivers the expected output for valid inputs: Tenants can register, log in, pay rent, and view payment history. Landlords can register, add properties, assign tenants, view payment reports, and manage maintenance requests. The system enforces role-based access — tenants cannot access landlord views and vice versa. Automated notifications are delivered upon successful payment or maintenance status change.  2.2.4 High-Order Testing High-order testing will evaluate the system under conditions beyond normal functional use: System Testing: End-to-end flow of the complete KRIB platform across all modules. Performance Testing: Verifying that the system responds within acceptable time limits under load. Security Testing: Confirming that unauthorized users cannot access protected routes or data. Recovery Testing: Validating system behavior after simulated failures (e.g., payment gateway timeout).  2.3 Testing Resources and Staffing Testing will be conducted by the developer in the role of tester, supported by the following resources: Hardware: Laptop running the local development environment (Django server + React frontend). Browser: Google Chrome (primary testing browser) and Mozilla Firefox (cross-browser check). Payment Sandbox: M-Pesa Daraja sandbox environment (Safaricom developer portal). Database: Local PostgreSQL instance seeded with test data.  2.4 Test Work Products The following work products will be produced as a result of the testing activities: Test Cases Document (this document — Section 3). Bug/Defect Log: A record of all identified defects, their severity, and resolution status. Test Execution Log: A chronological record of tests run, outcomes, and tester notes. Test Summary Report: A summary of overall test results submitted with the final project.  2.5 Test Record Keeping Test results will be documented as follows: A manual test log maintained in a spreadsheet, recording each test case ID, description, input, expected result, actual result, and pass/fail status. Backend console and application logs captured during test execution for debugging failed tests. Screenshots of key test outcomes (e.g., successful payment confirmation, error messages) stored for the final report.  2.6 Test Metrics The following metrics will be used The following scenarios will be tested: Login Integration: User submits login form → Backend validates credentials → JWT token issued → Role identified → Correct dashboard displayed. Payment Integration: Tenant submits payment → Django API validates → Request sent to M-Pesa Daraja → Transaction confirmed → Database updated → Receipt generated → SMS notification sent to tenant and landlord. Maintenance Integration: Tenant submits request → Backend logs request → Database updated → Notification triggered to landlord → Status reflected on both dashboards.  Expected Results: Each integration scenario produces the correct chain of outputs with no broken links between modules. Pass/Fail Criterion: All data flows must complete end-to-end without errors for the integration tests to pass.  3.2.3 Validation Testing Validation testing confirms the system satisfies the requirements in the KRIB SRS. Verify that the system does not record an incomplete payment and displays an appropriate error to the user. Restart the server and confirm system stability. Expected Result: No partial transaction is recorded; the system recovers gracefully and allows the user to retry.  3.2.4.2 Security Testing Procedure: Attempt to access Landlord dashboard routes while logged in as a Tenant. Attempt to access protected API endpoints without a valid JWT token. Verify that all sensitive routes are protected by role-based access control. Expected Result: Unauthorized access attempts are blocked with appropriate error responses (HTTP 401/403).  3.2.4.3 Performance Testing Procedure: Simulate multiple concurrent users (5–10 simultaneous requests) accessing the payment module and dashboard. Measure server response times and verify system stability under load. Expected Result: System responds within 3 seconds for standard operations under simulated load.  3.2.4.4 Alpha/Beta Testing Procedure: The KRIB system will be demonstrated to a small group of representative users (simulated landlords and tenants). Participants will perform key tasks: registering, paying rent, submitting maintenance requests, and viewing dashboards. Feedback will be collected and any usability issues recorded. Expected Result: Users are able to complete all core tasks without requiring assistance beyond the user manual.  Pass/Fail Criterion for All High-Order Tests: All critical defects identified during high-order testing must be resolved before system deployment.  3.3 Testing Resources and Staffing Testing is conducted by the project developer serving as the primary tester, using a laptopbased local development environment. For User Acceptance Testing, a small group of simulated users (peers or family) will be engaged to interact with the system.  3.4 Test Work Products Completed test cases table (this document). Bug/Defect Log with severity ratings (Critical, Major, Minor). Test Execution Log with timestamps and pass/fail results. Screenshots of key test outcomes included in the Final Report.  3.5 Test Record Keeping and Test Log All test activities are recorded in a test log maintained throughout the testing phase. The log documents the date of testing, the test case executed, the input used, the actual result observed, and the pass/fail outcome. Failed tests are escalated to the bug log with a description of the defect and its severity. After a bug is resolved, the affected test case is re-executed and the result updated in the log.
