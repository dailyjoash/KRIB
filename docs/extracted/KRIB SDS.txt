The document translates the functional and non-functional requirements defined in the Software Requirements Specification (SRS) into a structured technical design that will guide system development and implementation. The KRIB system is a web-based digital rental management platform designed to automate rent collection, manage tenant–landlord interactions, track maintenance requests, and securely store rental documents. The system integrates external services such as online payment gateways and notification services to enhance efficiency, transparency, and reliability within the rental management process. This SDS is intended for software developers, system architects, project supervisors, and testers. It serves as a reference for understanding how the KRIB system components interact, how data flows within the system, and how business rules are enforced through system processes. The design presented in this document ensures scalability, security, and maintainability while aligning with the project’s objectives and constraints.  2.0 Business Rules The KRIB system operates under a defined set of business rules that govern how rental management activities are executed within the system. These rules ensure consistency, data integrity, security, and transparency across all system operations. User Registration Rule Every user must be registered in the system with a unique identifier before accessing any system functionality. Users are assigned roles as either Landlord or Tenant, which determine their access privileges. Property and Tenant Onboarding Rule A landlord must register a property in the system before a tenant can be associated with it. Tenants can only be onboarded through an invitation or assignment by the landlord. c) Lease Activation Rule A lease agreement must be created and activated before rent payments or maintenance requests can be processed. Only tenants with active leases are permitted to use transactional features. d) Rent Payment Rule Rent payments can only be initiated by tenants and must be made using approved digital payment methods such as M-Pesa or card payments. All payments must be successfully verified by the payment gateway before being recorded in the system. e) Payment Validation Rule A rent payment is considered valid only if the payment amount matches the required rent amount for the specified billing period. Invalid or incomplete transactions are rejected and not stored in the database. Arrears Rule If rent is not paid by the due date, the system automatically flags the tenant account as being in arrears and updates the landlord’s dashboard accordingly. Maintenance Request Rule Only active tenants are allowed to submit maintenance requests for the specific property they occupy. Each request must include a description of the issue and is tracked by status until resolution. Document Management Rule All uploaded documents, including lease agreements and payment receipts, must be securely stored and accessible only to authorized users associated with the property. Notification Rule The system must send automated notifications (SMS or in-app) to relevant users upon successful payments, overdue rent, or updates to maintenance requests. Data Security and Access Rule User data and transaction records must be protected from unauthorized access. Role-based access control is enforced to ensure users only view or modify information relevant to their role. 3.0 Process Modeling  3.1 Context Diagram /The Context Diagram represents the system boundaries. The layout follows a modular and responsive design approach to ensure usability across different screen sizes, including desktops, tablets, and smartphones. 5.1.1 Website Layout Header Section The header appears at the top of every page and contains the system logo, application name, and essential navigation controls such as profile access and logout functionality. It provides consistent branding and quick access to core user actions. Navigation Section (Sidebar / Menu) The navigation menu is role based and dynamically adjusts depending on whether the user is logged in as a landlord or a tenant. Tenant Menu: Dashboard, Pay Rent, Maintenance Requests, Documents, Profile Landlord Menu: Dashboard, Properties, Tenants, Payments, Maintenance, Reports, Profile This separation ensures users only view features relevant to their role, enhancing security and usability. c) Main Content Area The main content area displays the core functionality selected from the navigation menu. Content is presented using cards, tables, and forms to improve readability and interaction. Dashboards provide summarized information such as rent status, arrears, recent payments, and maintenance updates.  5.1.2Design Characteristics Responsive Design: The interface is designed to automatically adjust to different screen sizes using responsive web design techniques, ensuring consistent usability on mobile and desktop devices. ComponentBased Design: The frontend uses reusable components to promote consistency across pages and simplify future system maintenance and expansion. Minimal and Clean Interface: A simple color scheme and uncluttered layout are used to reduce cognitive load and allow users to focus on core tasks such as payments and request tracking.  Accessibility Considerations: Clear labels, readable font sizes, and intuitive icons are used to enhance accessibility for users with varying levels of technical proficiency. Page Flow Overview User accesses the Login/Register page. Upon successful authentication, the system identifies the user role. The user is redirected to the appropriate dashboard (Tenant or Landlord). Navigation between system modules is handled through the sidebar menu. Users can log out from any page using the header controls. 5.2 Pseudocode 5.2.1 System Login and Role Routing BEGIN DISPLAY Login Form INPUT username, password  IF credentials are valid THEN     GET user role     IF role = Tenant THEN         REDIRECT to Tenant Dashboard     ELSE IF role = Landlord THEN         REDIRECT to Landlord Dashboard     ENDIF ELSE     DISPLAY Invalid Login Details ENDIF END 5.2.2 Rent Payment Process BEGIN INPUT paymentAmount, paymentMethod, tenantID  IF tenantID is valid AND lease is active THEN     IF paymentAmount = rentDue THEN         SEND payment request to Payment Gateway         RECEIVE transactionStatus          IF transactionStatus = SUCCESS THEN             STORE payment details in database             GENERATE receipt             SEND notification         ELSE             DISPLAY Payment Failed         ENDIF     ELSE         DISPLAY Incorrect Amount     ENDIF ELSE     DISPLAY Invalid Tenant or Lease ENDIF END 5.2.3 Maintenance Request Process BEGIN INPUT issueDescription, urgencyLevel, tenantID  IF tenant has active lease THEN     CREATE maintenance request     SET status = Pending     STORE request in database     NOTIFY landlord ELSE     DISPLAY Unauthorized Request ENDIF END                 5.3 Flow Chart (User Journey)   /
